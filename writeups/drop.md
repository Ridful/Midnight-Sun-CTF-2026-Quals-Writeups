## Challenge Writeup: drop (Midnight Sun CTF)

This challenge, titled **drop**, is a classic Return-Oriented Programming (ROP) challenge with a twist: the gadget pool is dynamically generated at runtime based on a predictable seed.

---

### 1. Analysis of the Environment

When connecting to the service, we are presented with a memory address: `mem: 0xc0d3000`. Based on the provided source code and exploit script, we can reconstruct the server's behavior:

- **Memory Setup**: The server allocates a large chunk of memory (8 MiB) at a fixed address: `0xc0d3000`.
    
- **Dynamic Gadgets**: It fills this memory with random integers generated by `rand()`.
    
- **Predictable Seeding**: The `srand()` seed is derived from the system time: `seed = time() - time() % 5`. This means the seed only changes every 5 seconds, making it trivial to replicate the "random" data locally.
    
- **Permissions**: After filling the memory, it uses `mprotect` to set the region to **Read + Execute (R+X)**. This turns 8 MiB of random data into a massive, predictable "gadget pool."
    
- **The Primitive**: The server reads `0x200` bytes into a private, non-executable buffer and then performs a stack pivot or register clearing routine that effectively starts a ROP chain from our input.
    

---

### 2. The Obstacles

1. **No Direct Execution**: The buffer where we write our initial ROP chain is non-executable. We cannot simply jump to our shellcode.
    
2. **No Info Leak**: We don't know the address of our initial buffer, but we _do_ know the address of the large RX (Read+Execute) region at `0xc0d3000`.
    
3. **Fragmented Gadgets**: Because the memory is filled with `rand()`, we don't have standard libc gadgets. We have to "mine" the 8 MiB of random data to find functional instructions like `pop rax; ret` or `syscall; ret`.
    

---

### 3. Exploitation Strategy

To get a shell, we need to execute an `execve("/bin/sh")` syscall. Since the random pool doesn't contain our shellcode, we use a three-stage attack:

#### Stage 1: Change Permissions

We use the ROP gadgets found in the random pool to call `mprotect(0xc0d3000, 0x1000, 7)`.

- **Address**: `0xc0d3000`
    
- **Size**: `0x1000` (one page)
    
- **Prot**: `7` (RWX - Read, Write, and Execute)
    
    This makes the start of our gadget pool writable.
    

#### Stage 2: Inject Shellcode

We use another ROP chain to call `read(0, 0xc0d3000, 0x200)`.

This allows us to send our actual shellcode over the socket and write it directly into the newly executable memory at `0xc0d3000`.

#### Stage 3: Pivot to Shellcode

After the `read` syscall returns, we point the ROP chain's next `ret` to `0xc0d3000`. The CPU jumps to our shellcode, and we get a shell.

---

### 4. Key Implementation Details

#### Gadget Mining

The helper C program `randgen.c` is crucial. By passing the same time-based seed, we generate an exact binary replica of the server's memory. The Python script then scans this binary for specific byte sequences:

- `\x58\xc3` -> `pop rax; ret`
    
- `\x5f\xc3` -> `pop rdi; ret`
    
- `\x5e\xc3` -> `pop rsi; ret`
    
- `\x5a\xc3` -> `pop rdx; ret`
    
- `\x0f\x05` -> `syscall` (Must be followed by a `ret` to keep the chain alive)
    

#### The Payload Structure

The final ROP chain sent to the server looks like this:

|**Purpose**|**Gadgets**|
|---|---|
|**Set up mprotect**|`pop_rax(10)`, `pop_rdi(base)`, `pop_rsi(0x1000)`, `pop_rdx(7)`, `syscall`|
|**Set up read**|`pop_rax(0)`, `pop_rdi(0)`, `pop_rsi(base)`, `pop_rdx(0x200)`, `syscall`|
|**Jump**|`p64(0xc0d3000)`|

---

### 5. Execution

1. **Sync**: The script calculates the current time bucket to match the server's `srand()` seed.
    
2. **Search**: It generates the 8 MiB blob and finds the offsets for the necessary ROP gadgets.
    
3. **Send ROP**: Sends the stage 1 & 2 ROP chain.
    
4. **Send Shellcode**: After the server's `read` call is triggered by the ROP chain, the script sends the raw `execve` shellcode.
    
5. **Profit**: The server executes the shellcode, giving us a remote command prompt.
    

> **Note**: The `sleep(1)` on the server side requires careful timing in the exploit script to ensure the ROP chain and the shellcode are sent at the correct moments.
